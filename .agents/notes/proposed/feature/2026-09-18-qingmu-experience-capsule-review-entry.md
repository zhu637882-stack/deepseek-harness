# Agent Note: Qingmu experience capsule promotion cockpit entry

Status: proposed

English | [中文](2026-09-18-qingmu-experience-capsule-review-entry.zh.md)

## Problem

The read-back half of the director experience channel shipped in [2026-09-16](2026-09-16-qingmu-experience-capsule-readback.md): `{{experience_capsules}}` renders the active store fresh on every assembly, and `mergeApprovedCapsules` pins the promotion semantics. That note recorded its own gap — "No operator UI yet. Promotion runs through the `promote_experience_capsules.py` CLI." The gap is still open, and the runtime root shows what it costs. `/Users/a1234/qingmu-native/experience-capsule-queue.json` holds five capsules the director submitted after real rejections (`SELF-cross-shot-read-last`, `SELF-guarded-save-fallback`, `SELF-closeup-frame-width-first`, `SELF-resave-unchanged-revision`, `SELF-two-shot-near-occlusion`); `/Users/a1234/qingmu-native/experience-capsules-active.json` holds the fourteen `EXP-*` capsules the one-time seed wrote and zero `SELF-*` capsules. In the two weeks since the write side shipped, nothing the director learned about itself has reached the director.

The CLI is not broken, it is unobserved. Promotion needs the live venv, the correct `--runtime-root`, `--list` to discover that anything is waiting, and the exact id to approve. No cockpit surface reports a queued lesson, so the step that closes the loop only happens when an operator remembers to ask. This is the same defect class the storyboard review gate and the asset audit entry were: the mechanism is finished and the harness has no entry point.

Two smaller defects sit under it. The submission tool read and rewrote the queue with a bare `readFile`/`writeFile`, so two capsules submitted close together could lose one, and a crash mid-write could leave a truncated queue. And `loadActiveCapsules` answers a corrupt store with `[]`, which is right for the persona — the director must still run — and wrong for a review panel, where an empty list reads as "nothing approved yet" and hides that no lesson is being injected.

## Proposal

One file layer, two Host routes, one cockpit panel, and the shared sign-in the panel is the fourth consumer of.

**A capsule file layer** — [experience-capsule-files.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/experience-capsule-files.ts) owns both files. `CAPSULE_ID` is the one id pattern, previously duplicated in the submission tool. `loadQueuedCapsules` and `loadApprovedCapsules` read strictly: a file over 1 MiB, a permission error, a non-array queue or invalid JSON raises `CapsuleStoreError` with the filesystem error as `cause`, while a missing file is the normal pre-first-write state and reads empty. `writeCapsuleFile` writes a temporary and renames it into place, so a reader sees either the old or the new content. `withCapsuleStoreLock` serializes every read-modify-write in this process through one promise chain; the submission tool and the promotion route both take it, so a capsule the director appends while a promotion writes is neither dropped from the queue nor approved unseen. The two Python operators cannot take this lock and are documented as deploy-time steps that run while no director session is submitting.

The submission tool in [experience-capsule-tools.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/experience-capsule-tools.ts) now runs its prune-append inside that lock and writes through the rename, keeping its own 30-day cutoff and duplicate-id refusal. `capsuleQueuePathFor` moved to [experience-capsule-store.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/experience-capsule-store.ts) beside `capsuleActiveStorePathFor`, so both paths resolve from one module, and `resolveCapsuleRuntimeRoot()` replaces the two copies of `process.env.QINGMU_RUNTIME_ROOT ?? process.env.QINGMU_NATIVE_ROOT ?? ''` that `model-tools.ts` carried. `parseActiveCapsules` was split out of `loadActiveCapsules` so the strict reader and the lenient persona reader share one validation, and `DEFAULT_RENDER_LIMIT` became the exported `ACTIVE_CAPSULE_RENDER_LIMIT` because the review state has to say which approved capsules actually reach the model.

**Two Host routes** — [experience-capsule-review.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/experience-capsule-review.ts) registers `GET /api/qingmu/experience-capsule-review` and `POST /api/qingmu/experience-capsule-review/promote`. The read answers one `qingmu-experience-capsule-review-v1` document: the render limit, how many approved capsules fall inside it, the queue with an `alreadyApproved` marker per entry, and the active store with `stages` always present and `injected` computed from position. The promotion body is exactly `{ confirmed: true, ids: [...] }`, capped at 8 KiB and 64 ids, every id matching `CAPSULE_ID` with duplicates refused; there is no approve-all form, so a decision always names the capsules the operator read. An id that left the queue since the panel read answers 409 with the missing ids, because the queue moved under the decision and the operator must look again.

Both routes require `isTrustedApiRequest`, and the promotion additionally requires `isHumanBrowserWrite`. A deployment with no runtime root answers 503 `experience_capsule_review_runtime_root_unconfigured` rather than an empty review, and a capsule file this process cannot read or write answers 503 `experience_capsule_review_store_unavailable`: "nothing is queued" and "the queue is unusable" must not look the same to the operator. The promotion writes the active store before it trims the queue, so a failure between the two leaves the capsule approved and still queued — a re-read shows both and re-promoting supersedes the stored entry — where the opposite order could drop an approved lesson silently.

The routes live in the bridge, not in the command adapter where the other human-review bridges sit: the adapter is a peer and dev dependency of the bridge, so an adapter route importing bridge state would be a cycle. The bridge imports `isHumanBrowserWrite`, `readJsonBody` and `jsonResponse` from the adapter through its `./src/*` export instead, and `isHumanBrowserWrite` is new in [human-browser-bridge.ts](../../../../packages/experimental/qingmu-yimeng-command-adapter/src/human-browser-bridge.ts), extracted from `browserWriteHeaders` so the origin, `authorization` and cookie checks have one copy across relaying and non-relaying routes.

Registration is a soft `ctx.inject(['webServer'], ...)` in [index.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/index.ts), inside a `host.effect(...)` that returns both disposers. The hard `export const inject = ['sessionProjections']` is unchanged, because the same package mounts in the director preset scope where there is no browser to serve; a composition without a Host web server still loads and simply serves no review route.

**A cockpit panel** — [ExperienceCapsuleReview.tsx](../../../../packages/experimental/client-ui-qingmu-cockpit/src/client/ExperienceCapsuleReview.tsx) reads once on mount and renders the queue as one checkbox per capsule with its symptom, rule, submission time and `alreadyApproved` marker, the counts line `待审 / 已入库 / 本次注入 n/12`, and the active store behind a `details`. The promote button is disabled until a capsule is ticked and sends only the ticked ids; the receipt replaces the state and echoes `promoted`. A 409 clears the ticks and re-reads so the next decision is against what is actually queued, and a 403 shows the sign-in form instead of guessing at the reason. The refresh button sits in an always-rendered action row, so a failed first read still offers a retry — that was absent until the client spec found it. A deployment without a runtime root renders nothing at all. Nothing here ticks, promotes or reloads on a timer: every promotion is one operator click. [QingmuCockpit.tsx](../../../../packages/experimental/client-ui-qingmu-cockpit/src/client/QingmuCockpit.tsx) mounts it twice, in the legacy `overview` tab and in the five-stage frame's delivery column behind a `details`; the two layouts are mutually exclusive branches of `applicationShell`, so one instance mounts.

**A shared sign-in block** — [human-session.tsx](../../../../packages/experimental/client-ui-qingmu-cockpit/src/client/human-session.tsx) holds `jsonObject`, `signInHumanSession` and the `HumanSessionSignIn` form that `EntityDraftHumanReview.tsx`, `StoryboardHumanReview.tsx` and `AssetReferenceAudit.tsx` each carried their own copy of. The asset audit note named this as deferred work; a fourth consumer made it due. The password stays inside the form and is dropped on success, so no panel state can log or resend it.

## Scope and blast radius

Harness only. No Writer change, no schema change, no migration, no live build or deploy: the code stops on branch `qingmu-self-learning-loop-20260916` for review. Neither route was invoked against the live stack while writing this, and no capsule file in `/Users/a1234/qingmu-native` was read for anything but the counts quoted above, which came from a read-only `json.load`. No capsule was promoted: promotion is the operator's decision and stays one. The routes call no provider, move no budget and write no Writer state — the only files they touch are the two capsule files. Login reuses the existing `/api/qingmu/editorial-handoff/human-session` route.

## Alternatives considered

**Keep the CLI.** Rejected. It is correct and stays useful for a scripted deploy, but it reports nothing on its own, and the loop's only human gate should be visible where the operator already looks. The on-disk shapes are unchanged, so both channels promote identically and neither invalidates the other.

**Let the director approve its own capsules.** Rejected. That is the gate: a lesson the director wrote about itself reaching its own next prompt without a human read is an unbounded self-write, which is why the write side has always landed in a queue rather than in the store.

**Auto-promote on submission when the queue is short, or on a schedule.** Rejected for the same reason, and it would also make the injected persona block change between turns for no decision anybody made, moving the prompt-cache prefix.

**Put the routes in the command adapter beside the other review bridges.** Rejected: the adapter is a peer and dev dependency of the bridge, so it cannot import bridge state without a cycle. Importing the shared fence through the adapter's `./src/*` export keeps one copy of the check without inverting the dependency.

**Poll the review route on a timer.** Rejected. The state changes only when the director submits or the operator promotes, both of which the operator can see for themselves; a timer would read two files forever to save one click on `重新读取`.

## Risks

**The panel was not verified in a real browser.** The live instance serves the deployed harness build, so it would show the previous UI, and a local run needs `build:lib:host` plus a web build on a disk with 11 GiB free, which is above this project's 10 GiB stop threshold but not by enough to spend on a build whose only purpose is one screenshot. The panel is instead exercised through 18 tests against a stubbed `fetch` that asserts the request URLs, methods, credentials, cache mode and bodies. That proves the component's own logic and not its rendered appearance; treat the wiring as tested and the layout as reviewed.

**The promotion fence is not authentication.** `isHumanBrowserWrite` requires no `authorization` header, an `origin` equal to the request's own `host`, and a syntactically well-formed `jason_token` cookie under 8192 bytes. It never verifies that cookie against the Writer's session store, which only the sign-in proxy can do, so a process on this machine that forges the origin header and a plausible cookie is let through. The fence keeps a page on another origin and an ordinary tool call from approving capsules; it does not keep out a determined local caller — and no such caller needs it, since both capsule files are already writable by any process running as this user. This is stated in the route JSDoc and in the bridge README's Known Limitations rather than left implied.

**Four branches are unreachable from a test.** `promote`'s `if (busy || ticked.length === 0) return` and `refresh`'s `if (busy) return` in the panel, and `submit`'s guard in `human-session.tsx`, all sit behind a `disabled` button: `fireEvent.click` on a disabled element never reaches the React handler, so no DOM-level test can cover them. The fourth is the `finally` cleanup arrow in `writeCapsuleFile`, which runs only when `rm` itself rejects. They are guards, not behaviour.

The repo's per-file 100% gate has no `packages/experimental` exclusion, and it is already red for this package: measured with their own specs, the committed `StoryboardHumanReview.tsx` reaches 93.61 / 83.56 / 92.85 / 98.64 and `AssetReferenceAudit.tsx` 84.44 / 72.36 / 92.85 / 92.30. The files this change adds are above both, and `experience-capsule-review.ts` is at 100 on all four. `human-browser-bridge.ts` measures 93.18 / 88.09 / 100 / 100 across both packages, with every remaining uncovered branch in `readJsonBody` and `writerCode`, which this change does not touch; `browserWriteHeaders` keeps its origin and `authorization` checks ahead of the cookie read, the order it had before the extraction, so a request carrying a service token is refused without its cookie being parsed and the existing refusal tests still reach both helpers. That is the reachable ceiling, not the configured one, and the gap is named here rather than closed by an exclusion.

**An unknown promotion outcome may have landed.** A 503 after the active store was written means the capsule is approved while its queue entry survives. The panel reports the failure and re-reads, and re-promoting supersedes rather than duplicates, but the operator has to read the state to learn which happened. There is no transaction across two files.

**`scene-planning.client.spec.tsx` flakes under whole-suite coverage.** Different tests in it fail on different runs; it passes alone and passes with `--no-file-parallelism`. It renders `ScenePlanningWorkspace`, which this change does not touch, so the flake is instrumentation timing rather than a regression here. The cockpit count above is taken from a `--no-file-parallelism` run for that reason.

**The two Python operators and the route can disagree about a concurrent write.** The lock is process-local. Running `promote_experience_capsules.py` while a director session is submitting is the one way to lose a queued capsule, which is why both scripts stay deploy-time steps.
