# Agent Note: Qingmu batch recovery and continuity observations

Status: implemented

English | [中文](2026-09-15-qingmu-batch-recovery-continuity.zh.md)

## Problem

Closing a tab lost the remaining authorized batch. Reusing a current draft could omit revision feedback. Sound-only cut reports did not assess visible continuity across edits, and the workflow exposed detailed controls before the main task.

## Decision

The existing batch command list persists in localStorage and submits under a browser Web Lock. Original request IDs survive recovery; conflicting legacy records stay intact. Feedback invalidates quotes and is carried into newly prepared requests within the pending or explicit retake scope. Concurrent draft edits prevent replacement; identical saved requests survive preparation retries.

The existing cut-review route accepts a versioned visual/audio rubric. Each adjacent-cut check needs observations on both sides; absent evidence stays unknown. Legacy audio reports and queued payloads retain their original method. Four navigation steps preserve all existing route URLs, with asset and storyboard preparation grouped together. Detailed shot controls expand on demand.

## Alternatives considered

**A new queue or director framework.** Existing server idempotency and review tasks already own these operations; a second owner would complicate recovery.

**Regenerate the whole episode after feedback.** This would discard selected scope and potentially replace acceptable work.

## Consequences

Recovery works in the same browser profile, not across devices. Web Locks require a supported secure browser context. Review results are model observations, not acceptance, and missing story or identity references limit their conclusions. No image or video is generated by these changes.
