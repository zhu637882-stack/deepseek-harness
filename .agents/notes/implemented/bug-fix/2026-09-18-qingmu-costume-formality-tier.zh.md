# Agent Note: 青木人物资产技能的礼仪规格档位

Status: implemented

[English](2026-09-18-qingmu-costume-formality-tier.md) | 中文

## 问题

人物资产技能只告诉导演如何克制服装装饰，从未告诉它如何选择服装等级，于是所有场合都塌进同一个克制的默认值。第1.1节有两道刹车——「身份高低不直接等于金色多少」与「选择与身份相关的三至五个辨识特征，不罗列整本服装词典」——却没有油门。因此登基、祭天、大朝会上的皇帝，与在案前批奏折的皇帝适用同一套规则；操作者对在线古装剧的反馈是皇上衣着不够华丽，而原因可能是没有细化，即设计没有落到具体部件。

缺的不是词汇量。同一节已经要求写清内外穿着层次、领襟和闭合方式、袖型与下装、腰带及鞋履，也要求以厚薄、垂坠、织纹与光泽区分面料并说明纹样位置和大小。缺的是在这些之前先定下当前场合究竟要求哪一档的那个决定：没有任何规则从场次推导礼仪规格，于是克制规则对礼服设计全额生效，读起来就成了可以省略该典礼自有必备件的许可。

补这个缺口意味着改动一份按哈希钉住的创作方法包，而它的来源登记是机械校验的。[skill-resources.ts](../../../../packages/experimental/qingmu-director-context-bridge/src/skill-resources.ts) 拒绝供给磁盘摘要与登记不符的资源，所以改了正文却没有重新登记摘要，结果不是更新技能，而是让导演彻底读不到它。

## 决策

[character-asset/SKILL.md](../../../../packages/experimental/qingmu-web/agent-presets/qingmu-director/skills/character-asset/SKILL.md) 现在把礼仪规格档位作为第1.1节的显式设计步骤，位置排在轮廓之前，因为档位决定了哪个轮廓才是对的。

档位由剧本当前场合推导，不由人物身份高低推导：皇帝日常批奏折是常服，登基、祭天、大朝会是冕服。真实历史题材使用该时代自有形制，技能中点名为常服、吉服、礼服、冕服；架空题材使用本片自定的同一条等级轴。每档各带一份必备件清单——冕服须写冠冕形制与旒数、上衣下裳分色、章纹的位置与数量、蔽膝、佩绶、玉带、舄履，礼服与吉服须写对应冠饰、袍服分色、章纹或补子、腰带与履——常服沿用原有的三至五个辨识特征。高档缺件记为设计未完成，而不是记为克制；剧本未写明场合时，导演按当前戏剧情境推导一档并标明推导，不默认常服。

档位由三个既有机制承载，没有新造机制。档位与该档必备件写入 `locked_features`。换档走第2节的变体后缀规则，所以皇帝的常服与冕服是两个带编号的变体，已审版本永不被覆盖。克制句保留原有力道，但写明它的支配者：装饰密度随礼仪规格档位升降。

同一档内的基准华丽度仍随身份升降：档位定上限，身份定下限。皇帝的常服是带盘龙团纹的织金赭黄绸袍，不是素袍；贫寒人家的礼服也不因落在高档而被镀金。这后半句是在线证据要求的，见下文影响。

第8节清单新增「礼仪规格档位已定，该档必备件写齐（无服饰角色标 not_applicable）」，这一条把规则变成资产必须通过的质量门，而不是导演可以跳过的散文。

[sources.json](../../../../packages/experimental/qingmu-web/agent-presets/qingmu-director/skills/sources.json) 重新登记 `character-asset` 的 `files["SKILL.md"]`，并扩写该条目的 `adaptation` 字符串——读取工具会把它与正文一并交给导演。`upstreamFiles` 仍指向上游修订 `678edc06`，`adaptedFiles` 本来就已列出 `SKILL.md`，所以该条目继续把自己报告为对一份 Apache-2.0 来源的青木适配，而不是上游原文。

## 备选方案

**放宽或删掉克制句。** 否决。「身份高低不直接等于金色多少」防的是相反的失败——因为某人有个头衔就给贫寒之家镀金——而本次缺陷是少了一个选择器，不是限值定错了。拆掉刹车会换来处处华丽，同时丢掉同一节要求的时代与身份可辨性。

**加一个由导演逐人设定的华丽度数值档。** 否决。一个脱离场合的数值档只是把原缺陷换个形式复现：导演仍然在凭品味选装饰密度，而第1.1节本来就写明这些包里的数值不是永久限制。由剧本陈述的事实——本场是哪一种典礼——推导出的档位，可以拿剧本去核对。

**把规则放进 `production-design`，本技能本来就先读它。** 否决。那个包与 `scene-asset`、`prop-asset` 共用，服装礼仪等级轴在场景与道具里没有指涉对象，而必备件清单是服装专属的。放在第8节服装清单能够强制执行的位置，才符合一事一处。

**改为同步上游 `ai-film-skills` 的新修订。** 否决。实测的上游修订并不带礼仪规格档位，同步并不能补上这个缺口；而且同步还得为一份登记表重算每个文件的摘要，而其中 `open-film-writer` 与 `open-film-camera` 两条在上游已不存在。同步本身仍然值得做，但应与本次修复分开。

## 影响

本次改动买到了操作者要的细化，而且是技能自己能核查的形式：导演必须先报出由场合推导的档位并逐项列出该档必备件，资产才能过质量门；常服与冕服因此变成两个锁定变体，而不是一份在各场之间漂移的设计。它也让克制规则读起来是有条件的而非绝对的，从而消掉了「典礼场面本该画得素净」这种解读。

代价是每个有服饰的人物多一个必填项，所以一个次要背景人物现在也需要显式档位或显式 `not_applicable`。必备件清单以中国宫廷为示例；非中国的历史题材必须映射自己那一套等价等级轴，技能写明以该时代自有形制为准，没有把这四个名称当成普适。

对生成服装的实际效果只能在一次真实资产运行中观察——没有测试断言导演会为大朝会选冕服，本次改动也没有补，因为那种断言测的是模型对散文的解读，不是代码路径。被机械钉住的是登记表不变式：[skill-resources.spec.ts](../../../../packages/experimental/qingmu-director-context-bridge/tests/skill-resources.spec.ts) 对每个打包文件重算摘要并与 `sources.json` 比对，同时要求 `adaptedFiles` 成员资格等于 `files` 与 `upstreamFiles` 不同，所以将来忘记更新摘要的改动会让测试失败，而读取工具在生产中失败关闭。该套件 759 个测试通过、2 个既有跳过。没有快照固件嵌入本技能的散文，所以 keyless 回放无需重录。

本次使用的适配机制，正是[创作方法 Agent Note](../architecture/2026-09-11-qingmu-creative-methods.zh.md) 确立的那一套。

对在线古装项目的只读核查塑造了规则的后半句，也关掉了一条假线索。皇帝最新存活的 turnaround——三个版本中唯一未被库删除的一张，且与本项目所有图像资产一样仍为 `Unselected`——与其 245 字设计逐项吻合：翼善冠双短翅无珠串、赭色圆领袍、细密暗纹织锦、胸前盘龙团纹、皮革腰带配玉扣、黑色布面靴俱在。所以「不够华丽」既不是渲染失败，也不是缺细节，而是设计自己的选词：暗赭金、深色玉扣、黑色布面靴，这正是身份下限现在要纠正的。同一次核查也否掉了场景侧的归因：针对「皇上位置在很多地方都不对」的伴随抱怨，御书房设计明确写出了中轴（北墙雕花御案、案后御座、御座后居中大座屏作为房间中轴标志），编译后的分镜提示词写明案后北侧、面朝南与显式机位坐标，所以生成帧里皇帝位置不对属于生成保真问题，归资产审计与镜头问题规则回路管，不是缺场景规则。基于这份证据没有新增任何场景规则。
