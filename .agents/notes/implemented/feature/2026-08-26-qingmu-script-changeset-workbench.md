# Agent Note: Qingmu script ChangeSet workbench

Status: implemented

English | [中文](2026-08-26-qingmu-script-changeset-workbench.zh.md)

## Problem

Qingmu OS could inspect Yimeng production facts, but it had no bounded write path. Sending edits through a generic Harness tool or exposing the Yimeng token to the browser would bypass Yimeng's revision, preview, idempotency, audit, and downstream invalidation contracts.

## Decision

The first write slice is limited to `episode_script`. A private Host command adapter owns the loopback-only `/qingmu-yimeng-command` channel and the `YIMENG_API_TOKEN`. It exposes only propose, preview, commit, and read-only commit-receipt recovery operations. The browser receives normalized results but never the token, cookies, arbitrary URLs, or a general HTTP proxy.

The Qingmu cockpit implements one explicit state machine: load the authoritative script and revision, edit a local JSON draft, propose a versioned ChangeSet, preview conflicts and invalidations, require a fresh anti-misclick acknowledgement, commit with a deterministic idempotency key, then re-read the authoritative script and workflow. Immediately before the commit `POST`, it must synchronously write and read back an exact minimal non-secret recovery marker in subject-scoped `sessionStorage`; a storage failure blocks the request. If the dialog, subject, or same tab is later closed, switched, or reloaded, the restored workspace offers only an explicit receipt query and never resubmits the commit. Recovery failures and lineage mismatches retain the marker and lock new edits. Only complete marker and receipt lineage plus a matching authoritative script reread can conditionally clear that exact marker. An explicit local-discard control exists for damaged or unrecoverable markers, but warns that it neither calls Yimeng nor undoes any server commit. The checkbox is user-interface friction, not identity authorization, security proof, or content signoff. Command authority comes from the Host-held token and Yimeng's authenticated owner and actor checks; human content signoff remains a separate workflow. A changed draft, proposal, preview, project, episode, failed commit, or response lineage clears the acknowledgement. Project id, episode id, ChangeSet id, payload hash, base revision, and idempotency mismatches fail closed. A post-commit script reread must also match the project, episode, authoritative revision, and `authoritativeSnapshotSha256` declared by the receipt. The read adapter hashes Yimeng's exact Python-canonical UTF-8 bytes, parses them, recursively rejects non-finite numbers and unsafe integers in both parsed projections, deep-compares the result with `script`, removes the canonical text, and exposes only the verified `scriptSha256`; the browser never reserializes the script across language runtimes. A mismatched reread cannot replace the confirmed UI snapshot; it preserves the receipt and marker and shows a warning.

Read and command traffic remain separate Host channels. Both adapters allow only pathless loopback HTTP(S) upstreams, reject redirects, omit cookies, bound request and response sizes, remove credential-shaped response fields, redact the active token from response keys and values, and return sanitized errors. Ordinary read responses remain capped at 5 MiB; only the script response has a 20 MiB hard cap so a legal command body near 5 MiB can still return both the parsed script and its escaped canonical evidence without creating an unbounded read. The public health request sends no Authorization header, while the Host uses the active token only as a recursive response-scrubbing secret. Project, episode, and base revision travel with propose, preview, and commit requests into Yimeng and are revalidated on the ChangeSet, preview, and commit receipt. Receipt recovery is the fourth command-adapter operation and performs one bodyless and queryless `GET` to the project/episode/ChangeSet-scoped command-receipt endpoint with the original `Idempotency-Key` header. The Host accepts only `jason.qingmu-command-receipt-recovery.v1`, recomputes the nested original receipt's canonical JSON SHA-256 before accepting `receiptSha256`, and revalidates its complete lineage, including a legitimate `deduplicated: false`. The Qingmu distribution overlay installs the read adapter before the command adapter and cockpit.

Yimeng remains the mutation authority. Propose validates project ownership before journaling; preview and commit validate project, episode, and base revision inside their transactions; persisted revisions must be non-negative integers, so fractional or boolean tampering fails closed as an integrity incident. Its commit transaction writes the script, revision, invalidations, command receipt, domain event, and audit journal. The initial outbox dispatcher is deliberately synchronous and accepts an injected sink: it validates journal and receipt lineage inside one SQLite write transaction, supports retry and backoff, and exposes `eventId` as the consumer deduplication key for at-least-once delivery. Current tests use an in-memory sink and there is no production worker wiring. The dispatcher core does not sandbox an arbitrary sink or enforce its network policy and timeout; those controls belong to a future production sink adapter.

## Alternatives considered

**Let the cockpit call Yimeng directly.** This would put the API token and network authority in browser code. The Host boundary keeps credentials and URL policy outside the client.

**Patch the script in one request.** This removes the visible preview and conflict boundary. The three-step ChangeSet protocol makes the proposed payload, authoritative revision, invalidation impact, and human commit decision independently observable.

**Use Harness sessions as the script source of truth.** Sessions are collaboration context, not Yimeng production state. The workbench always reloads Yimeng after commit and displays that authoritative result.

**Automatically retry commit after an interrupted response.** A retry could conceal the difference between transport uncertainty and a new user command. The workspace persists only non-secret lineage, requires an explicit read-only receipt query, and never resubmits the `POST` during recovery.

**Start with a network dispatcher or Provider worker.** That would expand operational and cost authority. The injected in-memory test sink proves integrity, retry, and idempotency semantics without external side effects; a policy-constrained production sink and worker wiring remain a separate stage.

## Verification

The 35 focused Harness tests (12 read-adapter, 7 command-adapter, 15 cockpit, and 1 bundle-order test) cover token isolation, public-health scrubbing, no-cookie requests, loopback-only URLs, ordinary and script-specific response byte limits, credential scrubbing, project/episode/base-revision lineage, exact canonical script evidence including Python `1e-06`, unsafe-integer rejection, forged script and receipt hashes, ChangeSet preview, conflict failure, acknowledgement invalidation, deterministic idempotency, strict recovery-marker storage, failure retention, explicit local discard, recovered receipt lineage, and authoritative refresh. The 47 focused Yimeng tests cover the opt-in schema gate, API and transaction vertical slice, revision conflict, idempotent replay, tamper detection, in-memory outbox retry and terminal failure, plus the existing script update and downstream invalidation contracts; 79 core production-gate regressions pass. The Qingmu profile build and one isolated real-Chromium journey exercise accepted commit → same-tab reload → explicit bodyless receipt recovery → authoritative reread while asserting that only one commit `POST` occurred. They do not use a formal database, paid provider, or production service.

## Consequences

Qingmu now has a narrow, auditable production-domain write workbench rather than a generic mutation surface. New targets must add their own Yimeng domain contract and UI state machine; they do not inherit script authority automatically. Recovery is intentionally limited to the current tab's `sessionStorage` lifetime. Discarding its marker restores local editing but cannot establish or reverse the server outcome. The ChangeSet schema and APIs default to disabled until explicitly enabled. Enabling the schema on the formal database, production worker wiring, production deployment, paid generation, and human content signoff remain outside this change and require their own authorization and evidence.
