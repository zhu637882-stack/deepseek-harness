# Agent Note: 青木导演接力账本与 Host 租约

Status: implemented

[English](2026-09-16-qingmu-director-relay-ledger.md) | 中文

## 问题

镜头批次的导演准备只在一个浏览器页面保持打开并持有会话时运行。关闭页面、连接中断或 Host 重启都会丢失进行中的工作，第二个操作者还能同时操作同一会话。没有任何持久记录说明人工已经授权、准备或排入队列表的镜头，因此中断后恢复可能为同一镜头重复付费。模型声称“保存成功”也可能被当作派发付费生成的依据。

## 决策

一个必填的类型化会话事件 `qingmu-director-relay/state` 以整体状态快照承载完整批次账本。`start` 保存项目、集、指令、被授权的导演提供方与模型、可选的被授权观察模型路线，以及有序镜头列表和每个镜头的参数与重做标记。`authorization` 保存显式 `paidConfirmed`、十进制 `maxCostCny`、`maxCandidates` 和 `expiresAt`。每个条目记录自身阶段与已收集的证据：已消费的导演请求、准备交接、素材请求、排队指令、公开运行状态，以及时间戳和原因。

`appendRelayState` 先比对观察到的 `revision` 再接纳下一份快照，因此落后的写入者不能覆盖更新的账本。批次输入与创建时间不可变，`completed` 与 `closed` 不再重开。已记录证据不可变：admissions 只追加，已有 admission 的镜头要新增必须显式从 `paused` 回到 `running`、且处于未过期预留内、并不能与交接或提交共存，交接与排队指令哈希不变，运行身份不变，成功或失败状态不回退。同一账本最多保留一笔未结算提交，总封顶成本与候选数不超过预留额度。这些整体规则在读取和追加时都执行，因此先前进程写坏的账本加载即失败，而不是继续消费。

记录意图不等于执行意图。`reserveRelaySubmission` 在任何派发之前写入确认后的精确排队指令，失败尝试同样消耗额度。所有接力效果路径先要求 `sessions.flush` 返回 true，并在每次 await 之后重新核对 admission。

浏览器与 Host 不能同时驱动一个会话。`claimHostDirectorBinding` 只在批次开放期间接管其镜头选择，`enter` 要求 `running` 且预留未过期，并且只能选择批次中列出的镜头范围。`withHostDirectorOperation` 与 `withHostDirectorStream` 在 await 和异步迭代器清理期间保持租约，进行中的工作时调用 `release()` 延后到该工作落定，持久化失败使租约失效但不释放。终态批次把会话归还浏览器，批次开放期间浏览器的 `enter`、`clear`、`bindProposal` 与 `recover` 均被拒绝。

`registerRelayExecutionGuard` 由可选装载的 model-tools 插件注册，只在批次预留该会话时施加这些门禁，普通轮次仍走原有路径。它要求本轮只有唯一被消费的 admission，把模型路线固定到被授权的导演模型，只为已记录的待处理工具请求在被授权观察路线上放行辅助调用，每次效果前刷新绑定，并拒绝成片剪辑保存、声学导入、经验胶囊提交以及涉及其他镜头的对白提交。

交接证据取自持久日志，而非助手文本。`readReferenceHandoff` 接受一条目标固定且与镜头一致的已消费 admission、一个 completed 轮次，以及该轮次中最后一次写入为已确认的 `qingmu_save_reference_draft`，其中带有范围、版本、请求、首帧、导演来源与上下文哈希。`verifyReferenceHandoff` 随后两次读取 Writer 上下文与已保存草稿，把漂移报告为 blocked。回环 `/qingmu-director-context` 门面以 `readReferenceHandoff` 暴露该能力。

## 考虑过的替代方案

**每一步一个事件**被否决：预算、候选数与单一活跃提交都是整体账本属性，压缩或部分重放会迫使读者自行重建这些结论。整体快照让每次追加校验都是整体的，代价是重写未变化的条目。

**在 Writer 或 SQLite 建批次表**被否决：会话日志是这批导演准备唯一的持久权威，第二个存储需要自身的恢复、关联键以及与日志的对账。

**由 Host 另开一个会话**被否决：准备延续同一对话、绑定、建议与后续人工审核，第二个会话会重复上下文，并让两侧对“什么已被批准”产生分歧。

**把报告保存成功的助手消息当作交接证据**被否决：模型文本既不持久也不权威；日志派生的证据可跨越压缩存活，且不能由执行工作的模型自行书写。

**批次运行时允许浏览器轮次**被否决，即使包含可能写入的只读轮次；一个会话只有一个写入者，页面只观察进度。

**排队响应丢失后自动重提**被否决：指令先记录，未定结果保持活跃，由人工处置而非可能重复付费的重试。**批次内并行提交**出于同样的记账理由被否决；见后果。

## 后果

关闭页面、重启 Host 或丢失一次排队响应不再丢失批次状态，恢复后的 Host 能区分已准备、已排队、运行中、已落定与不确定的镜头。重复付费被派发前预留、不可变指令哈希、未结算提交上限以及成本与候选总额共同阻止。自动工作与人工工作互斥且各自可审计，“已保存”的声称只在日志证明时被接受。

代价同样真实。每批候选一次只生成一个，时间收益受未结算提交规则限制而非导演限制。每个步骤重写完整账本，受 100 镜头上限约束，并且由于该事件读取时必填，这些快照会留在日志中。生产里还没有任何代码创建接力状态：既没有批次控制器，也没有页面控件驱动批次，因此账本、租约、门禁与交接读取是地基，需要后续改动接入工作区后才能供操作者使用。

## 测试

`relay-state.spec.ts` 直接对 schema 校验账本：授权与过期、各阶段所需证据、start 与 admissions 及交接、指令、运行身份、终态的不可变性、预算与候选总额、重试前先恢复、批次关闭。`bridge.spec.ts` 覆盖租约归属、晚于 release 的清理、失效、终态归还浏览器以及 JSONL 冷恢复。`reference-video-tools-composition.spec.ts` 用出厂预设与真实会话持久化驱动接力恢复与关闭，断言已关闭批次只在显式释放后才接受人工保存，且观察授权跟随批次。`rpc.spec.ts` 覆盖交接端点的会话、范围与漂移结果。
